## 5. `package.json`

`package.json` describes the Node.js application. It defines:

- Project name, version, and description
- **Scripts** (named commands)
- Dependencies and development dependencies
- Project configuration

Scripts used in this project:

```json
"scripts": {
  "test": "jest",
  "build": "if not exist dist mkdir dist && xcopy /E /I /Y src dist"
}
```

| Command | Runs |
|---|---|
| `npm test` | `jest` |
| `npm run build` | The build command |

> 💡 `test` is a special script name, so `npm test` works without `run`. Custom scripts like `build` need `npm run build`.

> ☕🐍 **Comparison:** `package.json` plays the role of Maven's `pom.xml` (Lesson 16) and Python's `requirements.txt` + `pyproject.toml` (Lesson 17) combined.

---

## 6. `package-lock.json`

`package-lock.json` records the **exact version** of every installed dependency — including dependencies of dependencies.

It guarantees the **same dependency versions** are installed in every environment: your laptop, a teammate's laptop, and the CI Runner.

> ✅ Always **commit** `package-lock.json`. CI depends on it (see `npm ci`, section 12).

## 7. Installing Jest

Jest was installed as a **development** dependency:

```bash
npm install --save-dev jest
```

Verify:

```bash

```

| Dependency type | Flag | Used for |
|---|---|---|
| `dependencies` | *(none)* | Needed when the app runs in production |
| `devDependencies` | `--save-dev` | Only needed for development/testing (like Jest) |

> 💡 `--save-dev` is the Node.js equivalent of Maven's `<scope>test</scope>` (Lesson 16).

> 💡 `npx` runs a tool from the project's own `node_modules`, without installing it globally.

## 12. `npm install` vs `npm ci`

| | `npm install` | `npm ci` |
|---|---|---|
| **Used for** | Development — adding or updating dependencies | CI — clean, reproducible installs |
| **Reads** | `package.json` (may update the lock file) | `package-lock.json` exactly |
| **Modifies `package-lock.json`** | Can | Never |
| **Existing `node_modules`** | Reused/updated | **Deleted** and reinstalled fresh |
| **If lock file and `package.json` disagree** | Resolves and updates | **Fails** with an error |

> ✅ For CI/CD pipelines, `npm ci` is preferred whenever a lock file exists.

> 🧠 **Analogy:** `npm install` is shopping from a **wish list** — you might get newer versions. `npm ci` is following an **exact receipt** — you get precisely what was bought before.

## 15. NPM Dependency Cache

```yaml
variables:
  NPM_CONFIG_CACHE: "$CI_PROJECT_DIR/student-node-api/.npm"

cache:
  key: npm
  paths:
    - student-node-api/.npm/
```

This caches npm's **download cache** between pipeline runs, reducing repeated downloads.

> 💡 **Why cache `.npm` and not `node_modules`?** `npm ci` **deletes** `node_modules` at the start of every run, so caching it would be wasted. Caching the npm download cache lets `npm ci` rebuild `node_modules` quickly from local files.

> ✅ The cache path uses `$CI_PROJECT_DIR`, so it stays correct after `cd student-node-api` (the trap from Lesson 16).

> 💡 The `key: npm` keeps this cache separate from the Maven and pip caches if all three languages share one `.gitlab-ci.yml` (Lesson 17).

## 16. Node.js Build

A build script was added to `package.json`:

```json
"build": "if not exist dist mkdir dist && xcopy /E /I /Y src dist"
```

```bash
npm run build
```

Generated:

```text
dist/
└── app.js
```

Verified with:

```cmd
dir dist
type dist\app.js
```

> ⚠️ **Windows-only:** `if not exist`, `mkdir`, and `xcopy` are **Windows CMD** commands. This works on your Windows Runner (npm runs scripts through `cmd.exe` on Windows), but it will **fail on Linux** — including the Docker and Kubernetes runners in later lessons. A cross-platform version using Node itself:
> ```json
> "build": "node -e \"require('fs').cpSync('src', 'dist', { recursive: true })\""
> ```

> 💡 In this lesson, the "build" simply **copies** the source. In real projects, a build usually **transforms** code — compiling TypeScript, bundling and minifying (e.g. with esbuild, webpack, or Vite). Angular (next lesson) is a good example of a real build step.

## 17. Complete GitLab CI/CD Pipeline

```yaml
stages:
  - test
  - build

variables:
  NPM_CONFIG_CACHE: "$CI_PROJECT_DIR/student-node-api/.npm"

cache:
  key: npm
  paths:
    - student-node-api/.npm/

node-tests:
  stage: test
  tags:
    - windows
  script:
    - cd student-node-api
    - node --version
    - npm --version
    - npm ci
    - npm test

node-build:
  stage: build
  tags:
    - windows
  script:
    - cd student-node-api
    - npm ci
    - npm run build
  artifacts:
    paths:
      - student-node-api/dist/
    expire_in: 1 week
```

> 💡 `npm ci` runs in **both** jobs because each job starts with a fresh checkout — `node_modules` from the test job is not automatically available to the build job.

### Optional: tidier version using `default` (Lesson 12)

```yaml
stages:
  - test
  - build

variables:
  NPM_CONFIG_CACHE: "$CI_PROJECT_DIR/student-node-api/.npm"

default:
  tags:
    - windows
  cache:
    key: npm
    paths:
      - student-node-api/.npm/
  before_script:
    - cd student-node-api
    - node --version
    - npm --version
    - npm ci

node-tests:
  stage: test
  script:
    - npm test

node-build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - student-node-api/dist/
    expire_in: 1 week
```

## 18. Pipeline Execution Flow

```text
                    Git Push
                       │
                       ▼
              GitLab CI/CD Pipeline
                       │
                       ▼
              ┌─────────────────┐
              │   Test Stage    │
              │  npm ci         │
              │  npm test       │
              └────────┬────────┘
                       │ SUCCESS
                       ▼
              ┌─────────────────┐
              │   Build Stage   │
              │  npm ci         │
              │  npm run build  │
              └────────┬────────┘
                       │ SUCCESS
                       ▼
                 dist/app.js
                       │
                       ▼
               GitLab Artifact ⬇️
```

The build stage runs **only after** the test stage succeeds.

> 🧠 **CI/CD principle:** Build should not proceed when required tests have failed.

## 20. Why Artifacts Are Important

Artifacts preserve anything a pipeline produces that must be used later:

- Compiled applications
- JAR files (Lesson 16)
- Python wheels (Lesson 17)
- Node.js build output
- Test and coverage reports
- Deployment packages

Typical production flow:

```text
Source Code
     ↓
Test
     ↓
Build
     ↓
Artifact
     ↓
Security / Quality Checks
     ↓
Deployment
```

> 🧠 **Build once, deploy the same artifact everywhere.** Later stages should use the artifact that was tested — not rebuild it.

To get GitLab's **Tests** tab (like Lessons 16 and 17), install a JUnit reporter:


Run Jest with it:

```yaml
node-tests:
  stage: test
  script:
    - npx jest --ci --reporters=default --reporters=jest-junit
  artifacts:
    when: always
    reports:
      junit:
        - student-node-api/junit.xml
```

`jest-junit` writes `junit.xml` in the project folder by default.

# 🔧 Troubleshooting & Practices

## 22. Troubleshooting

### Problem: npm build script missing

```text
npm error Missing script: "build"
```

**Cause:** The `build` script had not been added to `package.json` yet.

**Solution:** Add the script:

```json
"build": "if not exist dist mkdir dist && xcopy /E /I /Y src dist"
```

List all available scripts to confirm:

```bash
npm run
```

```text
available via `npm run`:
  build
```

Then run:

```bash
npm run build
```

> 💡 **Lesson 11 reminder:** In CI, also make sure the updated `package.json` was actually **committed and pushed** — a script that exists only on your machine will still be "missing" on the Runner.

## 24. Production CI/CD Best Practices

| # | Practice | Why |
|---|---|---|
| 1 | Commit `package-lock.json` | Reproducible dependency versions |
| 2 | Use `npm ci` in CI | Clean installs that match the lock file exactly |
| 3 | Don't commit `node_modules` | Large, generated, and reinstallable |
| 4 | Run tests before build | Never package broken code |
| 5 | Cache the npm cache directory | Faster `npm ci` |
| 6 | Store build output as artifacts | Later stages and people can use it |
| 7 | Use Runner tags | Jobs run on the right infrastructure |
| 8 | Keep CI configuration readable | Clear job names, stages, and `default` |
| 9 | Keep build scripts cross-platform | Pipelines can move to Linux/Docker runners |

## 27. Important Concepts

| Concept | Meaning |
|---|---|
| **Node.js** | Runtime that executes JavaScript outside the browser |

| **Build** | Prepares or transforms source code into build output |

## 28. Java vs Python vs Node.js Pipelines

| | Java (Lesson 16) | Python (Lesson 17) | Node.js (Lesson 18) |
|---|---|---|---|
| Config file | `pom.xml` | `requirements.txt` / `pyproject.toml` | `package.json` |
| Lock / exact versions | Versions in `pom.xml` | Pinned `requirements.txt` | `package-lock.json` |
| Install dependencies | Automatic in `mvn` | `python -m pip install -r requirements.txt` | `npm ci` |
| Test framework | JUnit | pytest | Jest |
| Run tests | `mvn test` | `python -m pytest` | `npm test` |
| Build | `mvn package` | `python -m build` | `npm run build` |
| Output | `.jar` | `.whl` / `.tar.gz` | `dist/` |
| Cache | `.m2/repository` | `.cache/pip` | `.npm/` |

> 🧠 Every language follows the **same CI pattern**: install dependencies → test → build → keep the artifact. Only the tools change.
